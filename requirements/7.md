# UnitMind UI 简化重构与复杂方法 Mock 识别修复需求

## 1. 当前问题

当前 UnitMind 右侧 Tool Window 已经能运行，但 UI 仍然不符合预期：

1. 页面风格不统一；
2. 有些页面是表格，有些页面是文字卡片，有些页面是空状态，整体割裂；
3. 信息区域太松散；
4. 第 1 步“方法确认”和第 2 步“概要”内容高度重复；
5. 参数约束页如果没有约束，整页只有一句话，体验很差；
6. Mock 策略页没有把复杂方法中的静态依赖、本类内部调用、局部对象依赖展示出来；
7. 测试代码页按钮过多，其中“重新生成代码”按钮不需要；
8. 用户可以通过“上一步 / 下一步”回退修改场景、Mock 策略后再生成，不需要在测试代码页单独放“重新生成代码”。

本次修改目标：**把 UnitMind 的每一页统一成表格风格，减少大段文字和空白，同时修复复杂方法 Mock 识别不出来的问题。**

---

## 2. UI 总体原则

### 2.1 所有步骤统一表格风格

除测试代码页外，所有页面都尽量使用表格展示。

页面包括：

```text

2 参数约束
3 测试场景
```

2. 不再保留单独的“方法确认”页；
3. 所有结构化信息都用表格；
4. 不要整页只有一句说明；
5. 空数据也要用表格展示，并给出原因行。

## 7. 第 4 页：Mock 策略

### 7.1 当前 Mock 不出来的原因

`BackupService#backup` 中没有典型的字段依赖，例如：

```java
private BackupRepository repository;
private JdbcTemplate jdbcTemplate;
private SomeClient client;
```

所以普通的 `@Mock` 字段识别为空是可以理解的。

但是该方法中存在大量**非字段依赖**：

```java
JdbcHelper.connect(request.dbConfig())
TableProfileResolver.resolve(connection, request.dbConfig())
FileUtils.deleteDirectory(backupDirectory)
```

这些属于**静态方法依赖**。

同时还有大量本类内部方法调用：

```java
includedPlans(profile, request)
resolveBackupTag(connection, plans, request)
clearSnapshot(connection, plans, backupTag)
copy(connection, plan, backupTag, request)
copyAttachmentFiles(connection, profile, plans, request, backupDirectory)
```

这些属于**本类内部调用依赖**。

当前插件没有识别这些依赖，所以 Mock 策略看起来为空。

---

### 7.2 Mock 策略页统一使用一个大表格

不要分成 Mock对象、when规则、verify规则、never规则四大块。

改成一个统一表格。

表格标题：

```text
Mock策略
```

表格列：

| 生成 | 依赖类型 | 对象/类名 | 方法 | 来源 | Mockito策略 | 备注 |
| -- | ---- | ----- | -- | -- | --------- | -- |

### 7.3 依赖类型

支持以下依赖类型：

```text
字段依赖
方法参数依赖
静态方法依赖
本类内部调用
局部对象依赖
不可直接Mock
```

### 7.4 对 BackupService#backup 的识别要求

至少识别以下行：

| 生成    | 依赖类型   | 对象/类名                | 方法                       | 来源                                | Mockito策略      | 备注                               |
| ----- | ------ | -------------------- | ------------------------ | --------------------------------- | -------------- | -------------------------------- |
| false | 方法参数依赖 | BackupRequest        | dbConfig()               | request.dbConfig()                | 构造测试对象         | Request DTO，不作为 Mock             |
| true  | 静态方法依赖 | JdbcHelper           | connect(...)             | JdbcHelper.connect(...)           | mockStatic     | 需要 mockito-inline                |

| false | 本类内部调用 | BackupService        | resolveBackupTag(...)    | this.resolveBackupTag(...)        | spy 或不处理       | private 方法不能直接 stub              |
| false | 本类内部调用 | BackupService        | clearSnapshot(...)       | this.clearSnapshot(...)           | spy 或不处理       | private 方法不能直接 stub              |
| false | 本类内部调用 | BackupService        | copy(...)                | this.copy(...)                    | spy 或不处理       | private 方法不能直接 stub              |

## 8. Mock 识别规则修复

### 8.1 不要把 DTO 参数当成 Mock

以下类型默认不要作为 `@Mock`：

```text
Request
Response
DTO
VO
BO
PO
Entity
Model
Command
Query
Param
Form
Result
```

例如：

```java
BackupRequest request
```

应该生成：

```java
BackupRequest request = new BackupRequest();
```

或者如果无法构造：

```java
// TODO: BackupRequest 无法自动构造，请根据业务补充测试数据。
BackupRequest request = null;
```

不要生成：

```java
@Mock
private BackupRequest request;
```

---

### 8.2 识别静态方法依赖

新增静态方法调用识别能力。

识别形如：

```java
ClassName.staticMethod(...)
```

例如：

```java
JdbcHelper.connect(...)
TableProfileResolver.resolve(...)
FileUtils.deleteDirectory(...)
```

将其加入 Mock 策略表，依赖类型为：

```text
静态方法依赖
```

Mockito 策略为：

```text
mockStatic
```

备注：

```text
需要 mockito-inline；如果项目没有该依赖，则生成 TODO 注释。
```

---

### 8.3 识别本类内部调用

识别当前类内部方法调用：

```java
includedPlans(...)
resolveBackupTag(...)
clearSnapshot(...)
copy(...)
copyAttachmentFiles(...)
```

加入 Mock 策略表。

依赖类型：

```text
本类内部调用
```

Mockito 策略：

```text
spy 或不处理
```

备注：

```text
如果是 private 方法，Mockito 不能直接 stub；建议作为真实逻辑执行，或后续重构为可注入依赖。
```

---

### 8.4 识别局部对象依赖

对于这种对象：

```java
Connection connection = JdbcHelper.connect(...)
```

应识别 `connection` 是来自静态方法返回值的局部对象依赖。

对其调用：

```java
connection.setAutoCommit(false)
connection.commit()
connection.rollback()
```

加入 Mock 策略表。

依赖类型：

```text
局部对象依赖
```

Mockito 策略：

```text
mock / verify
```

---

## 9. 第 5 页：测试代码

### 9.1 删除“重新生成代码”按钮

测试代码页不需要以下按钮：

```text
重新生成代码
```

原因：

用户可以通过底部：

```text
上一步
下一步
```

回到测试场景或 Mock 策略页面修改，然后再进入测试代码页生成。

### 9.2 保留按钮

测试代码页只保留：

```text
复制代码
恢复生成代码
格式化代码
```

说明：

1. `复制代码`：复制当前编辑器内容；
2. `恢复生成代码`：恢复 UnitMind 最初生成的代码；
3. `格式化代码`：格式化当前编辑器代码，MVP 阶段可以先 TODO。

### 9.3 测试代码编辑器

继续使用代码编辑器组件，要求：

1. 可编辑；
2. Java 高亮；
3. 有行号；
4. 写入时使用用户当前编辑后的代码。

## 10. BackupService#backup 的测试代码生成策略

该方法比较复杂，不要强行生成完全可运行的复杂测试。

MVP 阶段生成“可编辑草稿 + TODO 注释”即可。

### 10.1 如果支持 mockStatic

如果项目存在 `mockito-inline`，可生成：

```java
try (MockedStatic<JdbcHelper> jdbcHelperMock = mockStatic(JdbcHelper.class);
     MockedStatic<TableProfileResolver> resolverMock = mockStatic(TableProfileResolver.class)) {
    ...
}
```

### 10.2 如果不确定是否支持 mockStatic

生成 TODO 注释：

```java
// TODO: JdbcHelper.connect 是静态方法，若要 mock 需要引入 mockito-inline 并使用 mockStatic。
```

### 10.3 兜底测试代码

至少生成：

```java
package com.casc.datasync.service;

import com.casc.datasync.model.BackupRequest;
import com.casc.datasync.model.BackupResult;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

class BackupServiceTest {

    @Test
    void shouldBackupWhenRequestValid() {
        BackupService backupService = new BackupService();

        // TODO: 根据业务补充 BackupRequest 的 dbConfig、backupMode、includeAttachments 等字段。
        BackupRequest request = new BackupRequest();

        // TODO: JdbcHelper.connect 是静态方法，完整单测需要 mockStatic 或重构为可注入依赖。
        BackupResult result = backupService.backup(request);

        assertNotNull(result);
    }

    @Test
    void shouldThrowDataSyncExceptionWhenBackupFailed() {
        BackupService backupService = new BackupService();

        // TODO: 构造会触发异常路径的 BackupRequest。
        BackupRequest request = new BackupRequest();

        assertThrows(DataSyncException.class, () -> backupService.backup(request));
    }
}
```

注意：如果 `BackupRequest` 没有无参构造，改为：

```java
// TODO: BackupRequest 无法自动构造，请根据构造函数补充。
BackupRequest request = null;
```

## 14. 验收标准

### 14.1 UI 验收

1. 第 1、2 步合并为“方法概要”；
2. 方法概要页全部表格化；
3. 参数约束页全部表格化；
4. 测试场景页全部表格化；
5. Mock 策略页只用一个统一表格，不再分成多个大块；
6. 写入测试文件页表格化；
7. 测试代码页删除“重新生成代码”按钮；
8. 整体风格统一；
9. 不再出现整页一句话；
10. 不再出现大面积无意义空白。

### 14.2 Mock 识别验收

使用 `BackupService#backup(BackupRequest request)` 验证。

必须识别：

```text
JdbcHelper.connect
TableProfileResolver.resolve
FileUtils.deleteDirectory
includedPlans
resolveBackupTag
clearSnapshot
copy
copyAttachmentFiles
connection.setAutoCommit
connection.commit
connection.rollback
```

并在 Mock 策略表中展示。

### 14.3 DTO 参数验收

`BackupRequest request` 不允许作为普通 `@Mock` 对象。

应显示为：

```text
方法参数依赖 / 构造测试对象 / Request DTO，不作为 Mock
```

### 14.4 测试代码验收

1. 测试代码页有代码；
2. 代码可以编辑；
3. 不再有“重新生成代码”按钮；
4. 保留“复制代码”“恢复生成代码”“格式化代码”；
5. 写入时使用编辑后的代码。
