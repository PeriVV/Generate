# UnitMind 修改需求：修复大模型生成测试代码中的类型幻觉、private 方法调用和文件路径测试问题

## 1. 当前问题

UnitMind 接入大模型后，针对 `BackupService#copyAttachmentFiles(...)` 生成了测试代码，但生成结果存在明显错误。

典型错误包括：

1. 大模型编造了项目中不存在的类型：

```java
BackupRequest.DbConfig dbConfig = mock(BackupRequest.DbConfig.class);
```

导致 IDEA 报错：

```text
Cannot resolve symbol 'DbConfig'
```

2. 如果被测方法是 `private`，大模型仍然直接调用：

```java
backupService.copyAttachmentFiles(...)
```

这会导致编译失败。

3. 大模型过度 mock JDK 文件 API：

```java
MockedStatic<Files> filesMock = mockStatic(Files.class);
MockedStatic<Paths> pathsMock = mockStatic(Paths.class);
```

这不适合作为默认策略。

4. 大模型 mock 了 `Path backupDirectory`，导致路径安全校验失真：

```java
Path backupDirectory = mock(Path.class);
when(backupDirectory.resolve(anyString())).thenReturn(backupDirectory);
when(backupDirectory.normalize()).thenReturn(backupDirectory);
when(backupDirectory.startsWith(backupDirectory)).thenReturn(true);
```

5. 大模型没有获取 `request.dbConfig()` 的真实返回类型，直接猜了一个 `BackupRequest.DbConfig`。

6. 大模型不知道 `resolveAttachmentPath(scope, rs)` 和 `renderCondition(...)` 的真实实现，导致 ResultSet mock 可能不准确。

---

## 2. 修复目标

UnitMind 必须保证：

1. 不允许大模型编造项目中不存在的类型；
2. 对链式调用必须尽量解析真实返回类型；
3. 如果无法解析真实返回类型，使用 `RETURNS_DEEP_STUBS` 兜底；
4. private 方法不能直接调用，必须生成反射辅助方法，或者提示通过 public 方法间接测试；
5. 文件系统逻辑优先使用 `@TempDir` 和真实临时文件，不要默认 mock `Files`、`Paths`；
6. `Path backupDirectory` 优先使用真实临时目录，不要默认 mock；
7. 大模型生成代码后必须做一次类型校验和可编译性风险检查。

---

## 3. 修复链式调用类型幻觉

### 3.1 当前错误代码

```java
BackupRequest.DbConfig dbConfig = mock(BackupRequest.DbConfig.class);
when(request.dbConfig()).thenReturn(dbConfig);
when(dbConfig.resolveExistingFile(anyString())).thenReturn(sourceFile);
```

### 3.2 正确策略一：能解析真实类型时

UnitMind 应通过 PSI 或 JavaParser 解析：

```java
request.dbConfig()
```

的真实返回类型。

如果真实返回类型是：

```java
DatabaseConfig
```

则生成：

```java
DatabaseConfig dbConfig = mock(DatabaseConfig.class);
when(request.dbConfig()).thenReturn(dbConfig);
when(dbConfig.resolveExistingFile(anyString())).thenReturn(sourceFile);
```

### 3.3 正确策略二：无法解析真实类型时

如果无法确定 `dbConfig()` 返回类型，不允许生成 `DbConfig`、`BackupRequest.DbConfig`、`Config` 这类猜测类型。

应生成：

```java
BackupRequest request = mock(BackupRequest.class, RETURNS_DEEP_STUBS);
when(request.dbConfig().resolveExistingFile(anyString())).thenReturn(sourceFile);
```

并确保有：

```java
import static org.mockito.Mockito.*;
```

---

## 4. 大模型 Prompt 增加硬性规则

在发送给大模型的 Prompt 中增加以下约束：

```text
禁止编造项目中不存在的类型名。

对于链式调用，例如 request.dbConfig().resolveExistingFile(...)：
1. 如果上下文中提供了 dbConfig() 的真实返回类型，请使用真实类型；
2. 如果上下文中没有提供真实返回类型，不要猜测 DbConfig、Config、RequestConfig 等类型；
3. 无法确定中间返回类型时，使用 Mockito RETURNS_DEEP_STUBS；
4. 不要生成 BackupRequest.DbConfig，除非源码中明确存在这个内部类。
```

## 5. private 方法调用修复

### 5.1 当前错误

如果被测方法是：

```java
private int copyAttachmentFiles(...)
```

不能生成：

```java
backupService.copyAttachmentFiles(connection, profile, plans, request, backupDirectory);
```

### 5.2 正确生成方式

如果用户直接选择 private 方法生成测试，UnitMind 应生成反射辅助方法：

```java
private int invokeCopyAttachmentFiles(Connection connection,
                                      TableProfile profile,
                                      List<BackupTablePlan> plans,
                                      BackupRequest request,
                                      Path backupDirectory) throws Exception {
    Method method = BackupService.class.getDeclaredMethod(
            "copyAttachmentFiles",
            Connection.class,
            TableProfile.class,
            List.class,
            BackupRequest.class,
            Path.class
    );
    method.setAccessible(true);
    return (int) method.invoke(backupService, connection, profile, plans, request, backupDirectory);
}
```

测试方法中调用：

```java
int result = invokeCopyAttachmentFiles(connection, profile, plans, request, backupDirectory);
```

并补充 import：

```java
import java.lang.reflect.Method;
```

## 6. 文件系统测试策略修复

### 6.1 不要默认 mock Files 和 Paths

当前大模型生成：

```java
try (MockedStatic<Files> filesMock = mockStatic(Files.class);
     MockedStatic<Paths> pathsMock = mockStatic(Paths.class)) {
    ...
}
```

这不适合作为默认策略。

### 6.2 推荐使用 @TempDir

对于文件复制、文件存在性、路径安全校验，优先生成真实临时目录测试。

示例：

```java
@TempDir
Path tempDir;

@Test
void shouldCopyAttachmentFileWhenFileExists() throws Exception {
    Path sourceFile = tempDir.resolve("source.txt");
    Files.writeString(sourceFile, "hello");

    Path backupDirectory = tempDir.resolve("backup");
    Files.createDirectories(backupDirectory);

    ...
}
```

这样：

```java
Files.isRegularFile(sourceFile)
```

可以真实返回 `true`，不需要 mock。

### 6.3 backupDirectory 不要 mock

错误：

```java
Path backupDirectory = mock(Path.class);
```

正确：

```java
Path backupDirectory = tempDir.resolve("backup");
Files.createDirectories(backupDirectory);
```

## 7. FileUtils.copy 策略

`FileUtils.copy(source, target)` 可以有两种策略：

### 7.1 默认策略：真实复制

如果 `FileUtils.copy` 是项目内部工具，且可以正常复制临时文件，优先不 mock，直接使用真实临时文件验证目标文件是否存在。

### 7.2 兜底策略：mockStatic

如果大模型判断 `FileUtils.copy` 有副作用或实现复杂，可以使用：

```java
try (MockedStatic<FileUtils> fileUtilsMock = mockStatic(FileUtils.class)) {
    fileUtilsMock.when(() -> FileUtils.copy(any(Path.class), any(Path.class)))
            .thenAnswer(invocation -> null);
}
```

但需要提示：

```java
// TODO: 如果项目未引入 mockito-inline，请改用真实临时文件复制方式。
```

## 8. 对 copyAttachmentFiles 的推荐测试结构

对于方法：

```java
private int copyAttachmentFiles(Connection connection,
                                TableProfile profile,
                                List<BackupTablePlan> plans,
                                BackupRequest request,
                                Path backupDirectory) throws Exception
```

推荐生成测试时：

1. JDBC 对象使用 Mockito：

    * `Connection`
    * `PreparedStatement`
    * `ResultSet`

2. 业务数据对象可以局部 mock：

    * `TableProfile`
    * `TableScope`
    * `BackupTablePlan`
    * `BackupRequest`

3. 文件路径使用真实临时目录：

    * `@TempDir Path tempDir`
    * `Path sourceFile = tempDir.resolve("source.txt")`
    * `Path backupDirectory = tempDir.resolve("backup")`

4. `request.dbConfig()` 返回类型如果无法确定，使用 deep stubs：

    * `BackupRequest request = mock(BackupRequest.class, RETURNS_DEEP_STUBS);`

5. private 方法用反射辅助方法调用。

## 9. 大模型输出后处理校验

大模型返回测试代码后，UnitMind 必须做一次后处理检查。

### 9.1 检查不存在的类型

扫描生成代码中的类型名。

如果出现如下类型：

```java
BackupRequest.DbConfig
DbConfig
DatabaseConfig
Config
```

但无法在当前项目 PSI、import、同包类、java.lang、JUnit、Mockito 中解析，则标记为风险。

UI 中提示：

```text
检测到疑似不存在的类型：BackupRequest.DbConfig。建议改用真实返回类型或 RETURNS_DEEP_STUBS。
```

### 9.2 检查 private 方法直接调用

如果被测方法是 private，但生成代码中直接调用：

```java
backupService.copyAttachmentFiles(...)
```

则提示：

```text
当前被测方法是 private，不能直接调用。已建议使用反射辅助方法。
```

或者自动修正为反射调用。

### 9.3 检查空 tearDown

如果生成：

```java
@AfterEach
void tearDown() {
    // 确保静态 mock 被释放
}
```

但实际没有任何资源释放逻辑，应删除该方法。

---

## 10. 清理无效代码

大模型生成的测试代码中不应包含无意义代码。

需要删除：

```java
@AfterEach
void tearDown() {
    // 确保静态 mock 被释放
}
```

如果静态 mock 已使用 try-with-resources 管理，不需要 `tearDown`。

删除未使用 import，例如：

```java
import com.casc.datasync.db.JdbcHelper;
import com.casc.datasync.model.BackupResult;
import org.junit.jupiter.api.BeforeEach;
import org.mockito.Mock;
```

除非代码实际使用它们。

---

## 11. 验收标准

使用 `BackupService#copyAttachmentFiles(...)` 验证。

生成测试代码必须满足：

1. 不出现无法解析的 `BackupRequest.DbConfig`；
2. 不出现编造的 `DbConfig`；
3. 如果无法解析 `request.dbConfig()` 返回类型，使用 `RETURNS_DEEP_STUBS`；
4. private 方法不直接调用，使用反射辅助方法；
5. 默认使用 `@TempDir` 构造真实源文件和备份目录；
6. 不默认 mock `Files` 和 `Paths`；
7. `backupDirectory` 不默认 mock；
8. 不生成空的 `tearDown`；
9. 不保留未使用 import；
10. 测试代码页顶部提示大模型生成代码可能需要人工确认；
11. 大模型返回后，UnitMind 能检测疑似不存在类型并给出警告。

---

## 12. 优先级

```text
P0：禁止大模型编造不存在类型
P0：无法解析链式调用返回类型时使用 RETURNS_DEEP_STUBS
P0：private 方法生成反射调用
P1：文件系统测试默认使用 @TempDir
P1：删除空 tearDown 和未使用 import
P1：大模型返回后增加类型风险检测
P2：进一步根据 resolveAttachmentPath/renderCondition 源码优化 ResultSet mock
```
