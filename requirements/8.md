# UnitMind 修改需求：删除未实现按钮，并接入大模型生成 Mock 策略与测试代码

## 1. 当前调整目标

当前 UnitMind 插件的 UI 已经基本及格，右侧 Tool Window、步骤式流程、表格化展示已经可用。接下来不要继续大规模改 UI，重点做两件事：

1. 删除“格式化代码”按钮，因为当前没有实现格式化功能，放在测试代码页会误导用户；
2. 接入大模型能力，让 UnitMind 从“规则生成测试代码”升级为“静态分析 + 大模型生成”的智能单元测试助手。

核心原则：

```text
静态分析负责识别：
- 被测类
- 被测方法
- 方法参数
- 返回类型
- 参数约束
- 分支结构
- 方法调用
- 依赖信息
- 异常路径
- 静态方法调用
- 本类内部调用

大模型负责决策：
- 应该生成哪些 Mock 策略
- 哪些对象需要 @Mock
- 哪些静态方法需要 mockStatic
- 哪些 DTO 应该构造测试数据
- 每个测试场景如何组织
- 最终 JUnit5 + Mockito 测试代码如何写
```

---

## 2. 删除测试代码页“格式化代码”按钮

### 2.1 当前问题

测试代码页现在有按钮：

```text
格式化代码
```

但是当前并没有真正实现格式化功能。这个按钮放在页面里会让用户误以为可以格式化代码，实际点击后没有效果或只是 TODO，体验不好。

### 2.2 修改要求

从测试代码页删除：

```text
格式化代码
```

保留以下按钮：

```text
复制代码
恢复生成代码
```

如果当前还有：

```text
重新生成代码
```

也不要保留在测试代码页。用户可以通过“上一步 / 下一步”回到测试场景或 Mock 策略页面重新生成，不需要在测试代码页单独放重新生成按钮。

### 2.3 最终测试代码页按钮

测试代码页只保留：

```text
复制代码
恢复生成代码
```

底部全局按钮仍然保留：

```text
上一步
下一步
重新分析
写入测试文件
```

## 3. 新增大模型接入能力

### 3.1 总体流程

UnitMind 的生成流程调整为：

```text
用户选择被测方法
        ↓
静态分析源码
        ↓
生成 MethodAnalysisResult
        ↓
参数约束由静态分析确定
        ↓
测试场景可由静态分析先给出候选
        ↓
将静态分析结果、源码片段、约束、场景、依赖信息发送给大模型
        ↓
大模型返回 Mock 策略 + 测试代码
        ↓
UnitMind 展示 Mock 策略表
        ↓
UnitMind 展示可编辑测试代码
        ↓
用户确认后写入测试文件
```

---

## 4. 参数约束仍然使用静态分析

### 4.1 重要原则

参数约束不要交给大模型自由判断。

参数约束必须继续由静态分析识别，例如：

* `if (id == null)`
* `if (name.isBlank())`
* `if (count <= 0)`
* `throw new IllegalArgumentException(...)`
* `Objects.requireNonNull(...)`
* `Assert.notNull(...)`
* `CollectionUtils.isEmpty(...)`

大模型可以读取这些约束，但不能随意覆盖静态分析结果。

### 4.2 UI 表现

参数约束页仍然展示静态分析结果表格。

如果没有识别到参数约束，仍然展示类似：

| 参数      | 类型            | 约束类型     | 条件表达式 | 安全输入               | 异常输入        | 来源          |
| ------- | ------------- | -------- | ----- | ------------------ | ----------- | ----------- |
| request | BackupRequest | 未识别到显式约束 | -     | 构造默认 BackupRequest | null 或缺字段对象 | 静态分析未发现直接判断 |

---

## 5. Mock 策略改为大模型生成

### 5.1 当前问题

复杂方法中很多依赖不是字段依赖，例如：

```java
JdbcHelper.connect(...)
TableProfileResolver.resolve(...)
FileUtils.deleteDirectory(...)
includedPlans(...)
copy(...)
connection.commit()
connection.rollback()
```

这些依赖靠简单规则很难决定怎么 Mock。

### 5.2 修改目标

Mock 策略表的数据来源改为：

```text
静态分析发现候选依赖
        ↓
大模型根据候选依赖判断 Mock 策略
        ↓
返回结构化 Mock 策略
        ↓
UnitMind 渲染 Mock 策略表
```

### 5.3 Mock 策略表字段

继续使用一个统一表格：

| 生成 | 依赖类型 | 对象/类名 | 方法 | 来源 | Mockito策略 | 备注 |
| -- | ---- | ----- | -- | -- | --------- | -- |

### 5.4 大模型需要判断的内容

大模型需要判断：

1. 这个依赖是否需要 Mock；
2. 是普通 `@Mock`、`mockStatic`、`spy`，还是不处理；
3. DTO / Request / Entity 是否应该构造对象，而不是 Mock；
4. 静态方法是否需要 `mockito-inline`；
5. 私有方法是否不能直接 stub；
6. 返回值应该怎么设计；
7. 哪些调用需要 `verify`；
8. 哪些异常路径需要 `thenThrow` 或 `doThrow`。

---

## 6. 测试代码改为大模型生成

### 6.1 当前问题

规则生成的测试代码质量有限，尤其是复杂方法：

* 很难决定 Mock 返回值；
* 很难决定异常路径；
* 很难处理静态方法；
* 很难处理 DTO 构造；
* 很难生成有意义的断言。

### 6.2 修改目标

测试代码生成由大模型负责。

UnitMind 只负责：

1. 收集静态分析上下文；
2. 组织 Prompt；
3. 调用大模型；
4. 解析大模型返回结果；
5. 展示代码；
6. 允许用户编辑；
7. 写入测试文件。

---

## 7. 新增 LLM 配置入口

### 7.1 设置窗口新增配置项

在 UnitMind 右上角“设置”中，新增“大模型配置”区域。

配置项包括：

| 配置项         | 说明                                           |
| ----------- | -------------------------------------------- |
| 是否启用大模型     | true / false                                 |
| API 地址      | OpenAI-compatible API URL                    |
| API Key     | 从环境变量或 IDEA 安全存储读取                           |
| 模型名称        | 例如 `gpt-4o-mini`、`deepseek-chat`、`qwen-plus` |
| 请求超时时间      | 默认 60 秒                                      |
| 最大输出长度      | 默认 6000                                      |
| 温度          | 默认 0.2                                       |
| 失败时是否使用规则兜底 | 默认 true                                      |

### 7.2 API Key 安全要求

禁止硬编码 API Key。

禁止出现：

```java
private static final String API_KEY = "sk-xxxx";
```

推荐方式：

1. 优先从环境变量读取：

```text
UNITMIND_API_KEY
```

2. 或使用 IntelliJ PasswordSafe 保存；
3. UI 中只显示脱敏后的 Key，例如：

```text
sk-****abcd
```

### 7.3 API 地址

支持 OpenAI-compatible 接口，例如：

```text
https://api.openai.com/v1/chat/completions
https://api.deepseek.com/v1/chat/completions
https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions
```

不要把具体供应商写死。

## 9. 大模型输入内容

### 9.1 输入对象

新增 `LlmGenerationRequest`，至少包含：

```java
public class LlmGenerationRequest {
    private String packageName;
    private String className;
    private String methodName;
    private String methodSignature;
    private String returnType;
    private String methodSourceCode;
    private String classFields;
    private String imports;
    private List<ParameterInfo> parameters;
    private List<ConstraintInfo> constraints;
    private List<TestScenario> scenarios;
    private List<DependencyInfo> dependencies;
    private String existingTestCodeSummary;
    private String testFramework;
    private String mockFramework;
}
```

### 9.2 传给大模型的内容

Prompt 中必须包含：

1. 被测类包名；
2. 被测类名；
3. 被测方法源码；
4. 方法参数；
5. 返回类型；
6. 静态分析识别到的参数约束；
7. 静态分析识别到的分支；
8. 静态分析识别到的方法调用；
9. 静态分析识别到的静态方法调用；
10. 静态分析识别到的字段依赖；
11. 静态分析识别到的异常；
12. 用户在测试场景表中勾选的场景；
13. 当前项目使用 JUnit5 + Mockito；
14. 需要输出完整测试类代码。

## 10. 大模型输出格式

### 10.1 必须要求大模型返回 JSON

不要让大模型只返回自由文本。

要求返回 JSON，格式如下：

```json
{
  "mockStrategies": [
    {
      "enabled": true,
      "dependencyType": "静态方法依赖",
      "target": "JdbcHelper",
      "method": "connect(...)",
      "source": "JdbcHelper.connect(request.dbConfig())",
      "mockitoStrategy": "mockStatic",
      "note": "需要 mockito-inline"
    }
  ],
  "testCode": "package ...完整 Java 测试类代码...",
  "warnings": [
    "BackupRequest 构造可能需要根据业务补充字段"
  ]
}
```

### 10.2 JSON 解析失败处理

如果大模型返回非 JSON，或 JSON 解析失败：

1. 尝试从 Markdown 代码块中提取 JSON；
2. 如果仍失败，进入失败状态；
3. 显示错误：

```text
大模型返回格式无法解析，请重试。
```

4. 如果启用了规则兜底，则使用规则生成一个最小测试类草稿。

## 11. Prompt 要求

### 11.1 System Prompt

建议：

```text
你是一个资深 Java 单元测试工程师。你需要根据静态分析结果，为指定 Java 方法生成 JUnit5 + Mockito 单元测试代码。参数约束以静态分析结果为准，不要编造不存在的参数约束。请判断合理的 Mock 策略，并生成可编辑、尽量可编译的测试代码。
```

### 11.2 User Prompt 核心要求

Prompt 中明确：

```text
请只返回 JSON，不要返回 Markdown。
```

明确测试代码要求：

```text
1. 使用 JUnit5。
2. 使用 Mockito。
3. 不要生成中文测试方法名。
4. 测试方法名使用英文。
5. DTO / Request / Entity 类型优先构造对象，不要默认 @Mock。
6. Repository / Mapper / Client / JdbcTemplate / RedisTemplate / RestTemplate / WebClient 可以 Mock。
7. 静态方法调用需要说明 mockStatic，如果不确定依赖是否存在，生成 TODO 注释。
8. 私有方法不要直接 stub。
9. 测试代码必须是完整 Java 测试类。
10. 不允许返回空代码。
```

## 12. 大模型生成失败时的兜底策略

### 12.1 不能空白

无论大模型失败还是返回异常，测试代码页不能空白。

### 12.2 兜底规则

如果启用了规则兜底，则生成最小测试类：

```java
class XxxTest {

    @Test
    void shouldExecuteMethod() {
        // TODO: 大模型生成失败，当前为 UnitMind 规则兜底测试草稿。
    }
}
```

### 12.3 UI 展示

测试代码页顶部或底部显示警告：

```text
大模型生成失败，当前显示规则兜底测试代码。
```

## 15. 大模型调用时机

### 15.1 推荐时机

进入“Mock策略”步骤时：

1. 如果大模型启用；
2. 如果还没有生成过 LLM 结果；
3. 调用大模型；
4. 获取 Mock 策略和测试代码；
5. Mock 策略页展示 LLM 返回的 Mock 策略；
6. 测试代码页展示 LLM 返回的测试代码。

### 15.2 避免重复调用

不要每次点击下一步都重复请求大模型。

只有以下情况重新调用：

1. 用户点击“重新分析”；
2. 用户修改测试场景后确认重新生成；
3. 用户修改大模型配置后重新生成；
4. 当前 LLM 结果为空或失败。

## 19. 验收标准

### 19.1 UI 按钮验收

1. 测试代码页不再出现“格式化代码”按钮；
2. 测试代码页不再出现“重新生成代码”按钮；
3. 测试代码页只保留“复制代码”和“恢复生成代码”。

### 19.2 大模型配置验收

1. 设置窗口中可以配置大模型；
2. API Key 不硬编码；
3. 支持 OpenAI-compatible API；
4. 可以关闭大模型；
5. 关闭大模型时使用规则兜底生成。

### 19.3 生成流程验收

1. 参数约束仍然来自静态分析；
2. Mock 策略由大模型返回；
3. 测试代码由大模型返回；
4. 大模型返回内容能展示在 Mock 策略表和测试代码页；
5. 大模型失败时不会空白；
6. 大模型失败时可规则兜底；
7. 写入测试文件时使用用户编辑后的测试代码。

### 19.4 代码质量验收

1. 不允许硬编码 API Key；
2. 不允许空测试代码；
3. 不允许把 DTO / Request 默认作为 `@Mock`；
4. 不允许生成中文测试方法名；
5. 大模型返回 JSON 解析失败时必须有错误提示；
6. 所有异常必须记录日志。
